# Changelog

## Unreleased

Changes since `IHM_RELEASE_0_5`. The SDK was verified against that tag;
everything in this section is what an SDK update has to absorb.

### Breaking Changes

- `GET /static/images/coaches/{filename}` is removed, and with it the fallback that answered a missing coach photo with a placeholder JPEG. Coach and user images go through the media API. Files under `STATIC_DIR` are still served as they are by the `/static` mount, so a missing one is now 404 (#438).
- The evaluation and template requests no longer take `referenceDateTimeUtc`: `POST /v1/evaluations`, `PATCH /v1/evaluations/by_id/{evaluation_id}`, `POST …/transfer`, `POST /v1/evaluations/templates`, `PATCH /v1/evaluations/templates/by_id/{template_id}` and `POST …/apply` answer 422 when it is sent, as every other route has since #109. Evaluation and template timestamps — created, updated, published, deleted — always come from the server clock; a client could previously backdate them (#435).
- `GET /v1/venues/by_id/{venue_id}` now requires an authenticated user (401 otherwise); it was public at `IHM_RELEASE_0_5`. `GET /v1/venues` requires one as before (#387 had opened it to anonymous callers and #307 withdrew that within this release, so relative to the last release it is unchanged). `GET /v1/venues/deleted` stays admin-only. The public website reads venues only through the new `GET /v1/public/venues` (plain list of live venues) and `GET /v1/public/venues/{publicId}`, which address venues by an opaque `publicId` and carry no integer `id`. The public projection returns `publicId`, `name`, `address`, `description`, `mapUri`, `isDefault`, `isFeatured`, `primaryVenueBadge` and `image`, a descriptor for the newest publicly viewable `venue_image` media link (#307, #424).
- Events carry a `version` (starts at 1) and `updatedBy`, both returned in every `EventResponse`. `PATCH /v1/events/by_id/{event_id}`, `PATCH …/correction`, `PATCH …/future` and `POST …/reschedule` now **require** `version` in the body (422 when missing); a version the event has moved past is refused with 409 `STALE_VERSION`, whose `detail` carries the current `version`, `updatedAt` and `updatedBy`. Every event mutation bumps the version, including cancel, undo-cancel, terminate, extend, delete and restore, which take no version themselves (#292, #434).
- Occurrences carry their own `version`, `updatedAt` and `updatedBy`, returned in every `OccurrenceResponse`: 1 with no author until the occurrence first changes, bumped by every change after. `POST …/occurrences/{occurrenceTimeUtc}/reschedule`, `…/cancel` and `…/undo-cancel`, and a one-off's `POST /v1/events/by_id/{event_id}/drop` and `…/reinstate`, now **require** `version` in the body (422 when missing); `undo-cancel` and `reinstate`, which took no body, take `{"version"}`. Drop and reinstate take the version of the one-off's single occurrence, not the event's. A version the occurrence has moved past is refused with 409 `STALE_VERSION`, whose `detail` carries the current `version`, `updatedAt` and `updatedBy`. The event's own `version` is not bumped by occurrence changes (#430, #411).
- Organizers and coaches are users, referenced by username. `organizerName` and every entry of `coachNames` on `POST /v1/events`, `PATCH /v1/events/by_id/{event_id}` and `PATCH …/future` must name an existing user → 404 `USER_NOT_FOUND` otherwise. Coaches are stored as rows keyed on the schedule rather than a JSON list; the response shape is unchanged. A hard-deleted user disappears from `coachNames`, and the events they organized pass to the super admin who deleted them; a soft-deleted user stays referenced (#386).
- Cancelling an occurrence deletes its `present` / `absent` / `late` attendance records after refunding any credit charged for it; `onLeave` / `onLeaveRequested` records are kept. A camp cancellation or programme termination does the same for every occurrence at or after the cutoff. A restored occurrence is unmarked, and marking it again charges through the ordinary path (#337).
- The `member` role is removed from the `Role` enum: `POST /v1/users/by_id/{username}/roles` and `DELETE …/roles/{role}` reject `member` with 422, and a data migration strips it from every stored roles list. It gated nothing; there is no membership tier — any registered user may be enrolled subject to the conflict gates and credit (#400, #290).
- An event's timetable now lives in a sequence of **schedules** rather than on the event, and an event keeps one id for life. `PATCH /v1/events/by_id/{event_id}/future` (the programme split) no longer creates a successor event: it closes the current schedule at the cutoff and opens the next on the **same** event, and returns that event. `continuedAsEventId` and `continuedFromEventId` are removed from `EventResponse`; `GET /v1/events/by_id/{event_id}/chain` and `GET /v1/myevents/by_id/{username}/{event_id}/chain` are removed (404). `untilTimeUtc` remains and is the cutoff — the current schedule's `effectiveUntilUtc`. Enrollments, attendance, occurrence overrides and credit accounts never move (#388).
- `EventUpdateFutureRequest` is reshaped: `effectiveDateTimeUtc` is now required and must be an occurrence start of the current schedule at least 30 minutes ahead (400 `EFFECTIVE_TIME_NOT_SESSION_BOUNDARY`, 422 `CUTOFF_TOO_SOON`); `title`, `description` and `visibility` are removed (422 — a programme is renamed by correction, never from a date); `sessions` is added; at least one schedule field is required. A split that clashes with another programme is blocked with 409 (#365, #366, #388, #288).
- `EventCorrectionRequest` loses `coachNames` (coaching is a change, made by a split) and gains `gender`, `dobOnOrAfterUtc`, `dobOnOrBeforeUtc`, `isFeatured` and `galleryUris` (#365).
- `POST /v1/events/by_id/{event_id}/cancel` and `/undo-cancel` are camp-only. A programme returns 400 `INVALID_EVENT_TYPE` (use `/terminate`); a one-off returns 422 `INVALID_STATE` (use `/drop`, which takes no effective time) (#306).
- "Cancelled" is no longer a whole-event state. Join-side enrollment flows (invite, assign, assign-trial, approve, accept, request) are refused with 422 `INVALID_STATE` only when the event has no live occurrence at or after now, so a terminated programme or a camp cancelled with a future cutoff keeps accepting members until that cutoff. Exit-side flows are unchanged (#369).
- A programme's recurrence rule is validated: weekly with `BYDAY`, and no `COUNT`, `UNTIL`, `EXDATE` or `INTERVAL` → 422 `INVALID_RRULE_FOR_PROGRAMME`. A one-off with an `rrule` → 422 `INVALID_RRULE_FOR_ONEOFF`. A camp rule carrying `UNTIL` → 422 `INVALID_RRULE_FOR_CAMP`: a camp's end is derived from `COUNT`, and a cutoff is written only by cancelling (#371, #388).
- Occurrence guards apply to every event type. A reschedule may only move an occurrence later → 422 `POSTPONE_ONLY` (replaces 400 `PAST_RESCHEDULE_TIME`); a reschedule or a cancellation inside the 30 minutes before the effective start → 400 `RESCHEDULE_LEAD_TIME_VIOLATED` / `CANCELLATION_LEAD_TIME_VIOLATED`; an occurrence whose slot is at or after the cutoff → 422 `CANCELLED_OCCURRENCE`, and the listing shows it cancelled whatever its override says; a duration change on an occurrence whose schedule carries a timetable → 422 `INVALID_SESSIONS`. Super-admin bypasses the lead-time, past and postpone guards as before (#372, #375, #380).
- Conflict detection is one module with venue, organizer, coach and member gates. Only a programme-against-programme clash blocks (409 on create and on split; 409 `TIME_CONFLICT` on join); every other pairing — a one-off or camp against anything, a programme against a camp or one-off — is reported to the admins via `event.conflict_detected` and proceeds. One-off creation therefore no longer returns 409 on a venue or organizer overlap. Overlap is per occurrence, so two programmes on different weekdays do not clash. `POST /v1/events/check-conflict` and `POST /v1/events/by_id/{event_id}/check-user-conflicts` accept every event type; the `EVENT_TYPE_NOT_SUPPORTED` rejection is gone from these two endpoints (a programme reschedule still returns it) (#382, #288, #17).
- The check-conflict schemas are renamed: `CampConflictCheckRequest` → `ConflictCheckRequest` and `CampConflictReport` → `ConflictReportResponse`; fields unchanged (#382).
- A camp or one-off whose first occurrence is more than the scheduling horizon ahead is refused with 422 `BEYOND_SCHEDULING_HORIZON`. The horizon is `SCHEDULING_HORIZON_WEEKS`, default 52; programmes are exempt (#383).
- Departure credit settlement is deferred when an occurrence the member is still enrolled for is under way: the `creditDisposition` supplied to `remove` or `approve-withdraw` is recorded and applied by the hourly sweep once that occurrence has ended, and the balance stays bound and spends normally until then. Where no such occurrence exists settlement is immediate, as before (#378).
- A deferred departure settlement, applied by the hourly sweep after the session under way has ended, now records the admin who stated the `creditDisposition`: `actorUsername` on its `penalty`, `transferOut` and `transferIn` entries, and `openedBy` on the general account it opens. They were null. The release of a terminated programme still records no actor (#448).
- `GET /v1/myevents/by_id/{username}/attendance` is filtered by what the member's enrollment covered at the time, not by its current status: a withdrawn or removed member keeps the records of sessions they attended, and a mid-series joiner does not see records predating `enrolledAtUtc` (#379).
- Restoring an item that is not soft-deleted answers 422 `NOTHING_TO_RESTORE` on every restore endpoint — events, users, venues, groups, evaluations, evaluation templates and media — replacing `NOT_DELETED` (evaluations answered `INVALID_STATE`). Hard-deleting an item that is not soft-deleted answers 422 `HARD_DELETE_NEEDS_SOFT_DELETE` on every hard-delete endpoint — events, users, venues, groups, evaluations, evaluation templates and media — replacing `NOT_DELETED` (groups), `INVALID_STATE` (users, evaluations, templates) and 409 `MEDIA_NOT_DELETED` (media); events and venues answered 500. `NOT_DELETED` and `MEDIA_NOT_DELETED` are retired (#526).
- Eligibility on events and groups is an **age band**, not two dates of birth. `POST /v1/events`, `PATCH /v1/events/by_id/{event_id}`, `PATCH …/correction`, `POST /v1/groups` and `PATCH /v1/groups/by_id/{group_id}` take `minAge` and `maxAge` — each `{years, months, days}` (years 0–150, months 0–11, days 0–30; months and days default to 0), `null` clearing the bound — and `strictAge` (default false). `dobOnOrAfterUtc` and `dobOnOrBeforeUtc` are no longer accepted on any write (422). `minAge` greater than `maxAge` → 422 `INVALID_STATE`. A group's `kind` is derived from having `gender` or an age bound (#16).
- `EventResponse`, the public event projection, `GroupResponse` and the group detail carry `minAge`, `maxAge`, `strictAge` and `eligibilityReferenceDayUtc`, and keep `dobOnOrAfterUtc` / `dobOnOrBeforeUtc` as the window worked out for that day, both ends inclusive. The reference day is the day a camp or one-off starts, a programme's next occurrence that is not cancelled (today when it has none), and today for a group. Strict admits ages exactly `minAge` to `maxAge` on that day; relaxed widens each end by a year less a day. Every eligibility check — invite, request, assign, approve, the eligible-user lists, the member's event and occurrence listings, auto-group membership, semi-auto add / request / approve and the criteria-edit check — uses this window, so a programme's and a group's window moves forward each day (#16).
- Days are the club's calendar days: add the deployment setting `CLUB_TIMEZONE`, an IANA zone name, default `Asia/Kolkata`; an unknown zone stops the server at startup. The migration converts each stored date bound to the strict age that reports the same date on the day it runs (#16).

### Breaking Changes: evaluations as items and answers

- Templates are a `name`, a `layout` and `items`; `description`, `scopes` and `categories` are removed. An item is one variant of a union selected by `type` — `rating`, `yesNo`, `singleChoice`, `multipleChoice`, `number`, `qa` or `info` — with its own properties only (422 otherwise). `POST /v1/evaluations/templates` takes `{name, layout}` with the items inline in the layout (`layout` entries are items or `{section, items}`, one level deep) and refuses a template with no question; reads return `layout` as item ids and sections, and `items` in layout order, each with its `id` (#535).
- Template items are edited one at a time: `POST /v1/evaluations/templates/by_id/{template_id}/items` `{item, section?}` (201, appended to the layout or to the named section), `PUT …/items/{item_id}` (replaces in place; a type change → 422 `ITEM_TYPE_FIXED`), `DELETE …/items/{item_id}` (also leaves the layout). `PATCH /v1/evaluations/templates/by_id/{template_id}` takes `{name?, layout?}`; a layout naming an item twice, missing one or naming another → 422 `INVALID_LAYOUT`. While any evaluation, soft-deleted included, uses a template, every item or layout change → 422 `TEMPLATE_IN_USE`; renaming stays allowed. An item of another template → 404 `ITEM_NOT_FOUND` (#535).
- Add `originItemId` on items: a copy of another template's question names its source, and the server records the first item of the chain. A copy that changes the type or answer domain → 422 `ORIGIN_MISMATCH`; an unknown origin → 404 `ITEM_NOT_FOUND`. Add `GET /v1/evaluations/templates/items?search=&type=` (staff), the items of every live template with `templateId` and `templateName` (#535).
- Evaluations name `createdFor`, `createdBy` (never changes), `owner` (set by a transfer) and `eventId` (null = general); `subjectUsername`, `authorUsername`, `scope`, `scores`, `comment` and `coachNote` are removed. `POST /v1/evaluations` takes `{templateId, createdFor, eventId?, periodStartUtc?, periodEndUtc?}` and requires the coach role — an admin, super admin included, gets 403. A period is allowed on a general evaluation. `PATCH /v1/evaluations/by_id/{evaluation_id}` takes `{eventId?, periodStartUtc?, periodEndUtc?}` on a draft: an omitted field keeps its value, `eventId: null` makes the draft general, and eligibility is checked again for the effective owner against the resulting event and period (422 `NOT_ELIGIBLE`, 404 `EVENT_NOT_FOUND`); `createdFor` is refused with 422. `POST /v1/evaluations/templates/by_id/{template_id}/apply` is removed (#535).
- Add `PUT /v1/evaluations/by_id/{evaluation_id}/answers/{item_id}` `{valueNum?, valueText?, choices?, coachNote?}` and `DELETE …/answers/{item_id}` (clears the answer and detaches its evidence). An answer that does not fit its item → 422 `INVALID_ANSWER`. Reads return `answers`, each `{itemId, valueNum, valueText, choices, coachNote, evidence: [{mediaUuid, metadata}]}` (#535).
- Only a draft is edited: answers, the period and evidence on a saved or published evaluation → 422 `INVALID_STATE`. `POST …/save` refuses a draft missing a required answer, or a coach note its answer requires, with 422 `INCOMPLETE` and `details.itemIds` (#535).
- Before publication an evaluation exists only for its effective owner (`owner`, else `createdBy`): anyone else — another coach, an admin — gets 404 `EVALUATION_NOT_FOUND` from every staff route, media included, and the staff listings show the caller's own evaluations only (`createdFor`, `eventId`, `general` and `status` filters; `authorUsername` and `scopeType` are removed). `GET /v1/myevaluations/…` is open to the member and to coaches, not to admins (403) (#535).
- `POST …/transfer` takes `{owner}` and answers 204 with no body. The effective owner may transfer, or an admin naming the evaluation by id; the new owner must hold the coach role → 422 `NOT_ELIGIBLE` (#535).
- The member view carries `template` (`id`, `name`, the layout and items without private ones) and the answers to public items; private items, their answers and evidence never reach it. The coach note on a public item is part of it. Evidence is media tagged with its question's id, on a question with `allowEvidence`, and only images, videos and PDFs → 422 `INVALID_EVIDENCE` otherwise; the `shared_` tag prefix is retired (#535).
- Publishing stores the evaluation's member copy — a PDF of the member view — as a media item linked under the tag `member_copy`, downloadable by the member and staff; publishing again replaces it and soft-deletes the old file. Add `GET /v1/evaluations/by_id/{evaluation_id}/pdf`, the owner's preview of the member copy at any status, never stored (#535).
- Templates are written by any staff member: `POST /v1/evaluations/templates`, `PATCH …/by_id/{template_id}`, the item `POST`/`PUT`/`DELETE`, `DELETE …/by_id/{template_id}`, `POST …/restore` and `GET /v1/evaluations/templates/deleted` admit a coach as well as an admin; a member gets 403. Hard delete stays super-admin (#535).
- A live template's name is unique, compared without regard to case or surrounding spaces: `POST /v1/evaluations/templates`, a rename on `PATCH …/by_id/{template_id}`, and `POST …/restore` of a template whose name a live one now holds answer 422 `TEMPLATE_NAME_TAKEN`. A soft-deleted template holds no name (#535).
- A review period lies in the past: on `POST /v1/evaluations` and `PATCH /v1/evaluations/by_id/{evaluation_id}`, a `periodEndUtc` later than the server's clock answers 422 `PERIOD_IN_FUTURE`. `periodEndUtc` may now equal `periodStartUtc` (a one-day period); an end before the start, or one bound alone, is still refused with 422 request validation (#535).
- A coach holds one live review per member, template and period — the exact `periodStartUtc` and `periodEndUtc`, or none; overlapping periods differ and the event is not part of the key. `POST /v1/evaluations`, a period or event change on `PATCH /v1/evaluations/by_id/{evaluation_id}`, `POST …/transfer` to a coach who already owns the twin, and `POST …/restore` while the twin is live answer 422 `DUPLICATE_EVALUATION` (#535).
- The member copy PDF prints a written (Q & A) answer in its table row, in layout order; only the Q & A questions closing the layout at its top level print after the table (#535).
- Template reads carry `inUse`: whether any evaluation, soft-deleted included, is written against the template, so its items and layout are frozen (#535).
- Add `POST /v1/evaluations/by_id/{evaluation_id}/evidence/{item_id}` (multipart `file`, 201, the staff view): the owner uploads evidence for one question of a draft in one step; the file is stored with the evaluation's member as uploader and access roles `self`, `coach`, `admin` — never public. An unsupported file kind → 422 `INVALID_EVIDENCE`; too large → 413 `FILE_TOO_LARGE` (#535).
- Only save, publish, unpublish, revert, transfer and hard delete write audit rows; creating, editing and deleting a draft, restoring it, and evidence changes do not (#535).

A category change is refused with 422 `TEMPLATE_IN_USE` while a soft-deleted evaluation references the template, as it is for a live one (#486).
- Refuse `DELETE /v1/evaluations/by_id/{evaluation_id}/hard` and `DELETE /v1/evaluations/templates/by_id/{template_id}/hard` on a live evaluation or template with 422 (`HARD_DELETE_NEEDS_SOFT_DELETE` since #526): it must be soft-deleted first, as every other entity must (#487).
- Refuse an evaluation author who is not a coach or an admin with 422 `NOT_ELIGIBLE`, in every scope, on `POST /v1/evaluations` and `POST …/transfer`; general scope accepted any active user (#488).
- Accept `ownerType=evaluation` on `GET /v1/media/links` and filter by it, whether or not the evaluations module is on; it answered 422 `INVALID_OWNER_TYPE` (#489).
- Hand the evaluation templates a hard-deleted user created, live or soft-deleted, to the super admin who deleted them (`createdBy`), as their events are; they were deleted with the user, and the user's hard delete answered 500 when an evaluation used one (#490).

### Bug fixes: scheduler and credit

- Reject a `creditDisposition` on `remove` and `approve-withdraw` whose `validUntilUtc` is not after `validFromUtc` or has already passed, with 422 `VALIDATION_ERROR`; it used to fail with 500 when settled at once and block every hourly sweep when deferred (#476).
- Send `attendance.absence_streak_warning` once per streak: a later non-absent mark ends the streak, a growing streak is not warned again, and a streak already warned is not warned again after its notification expires (#478).
- Send `event.upcoming_reminder` and `attendance.pending_mark_reminder` for every occurrence of a programme or camp, not only the first; `occurrenceTimeUtc` / `occurrenceEndTimeUtc` name the occurrence. No upcoming reminder is sent for a cancelled occurrence or one at or after the event's cutoff (#475).
- Reopen a closed credit account when a session refund (cleared attendance or a cancelled occurrence) lands in it: its `state` is no longer `closed`, so the refunded credit can be spent, extended or transferred again, and the reopening is audited as `reopen_credit_account` (#479).
- Settle a deferred departure's `creditDisposition` as stated even when its validity window has closed by settlement time: the window is checked only when it is stated. Each departure in the hourly sweep settles on its own, so one that fails is logged and retried next sweep without holding up the rest (#485).

### Bug fixes: event lifecycle
- Answer 404 `EVENT_NOT_FOUND` to every mutation of a soft-deleted event — update, correction, split, cancel, undo-cancel, reschedule, terminate, extend, drop and reinstate — whatever its type; restore it first (#471).
- Reject marking attendance or requesting leave for a time that is not an occurrence of the event's schedule with 422 `INVALID_OCCURRENCE_TIME`, and answer 404 `EVENT_NOT_FOUND` to a leave request on a soft-deleted event (#470).
- Apply cancel's guards to `POST /v1/events/by_id/{id}/occurrences/{t}/undo-cancel`: a past occurrence answers 422 `PAST_OCCURRENCE` and one within 30 minutes of its start 400 `CANCELLATION_LEAD_TIME_VIOLATED`, unless a super-admin overrides, in which case no notification is sent; a slot at or after the cutoff answers 422 `CANCELLED_OCCURRENCE` (#474).
- Count a postponed occurrence as live until its new end: joins stay open and exits are not treated as past while a rescheduled session is still ahead, even once its original slot has passed. `POST /v1/events/by_id/{id}/occurrences/{t}/reschedule` now answers 422 `INVALID_STATE` for a one-off; move a one-off with `POST /v1/events/by_id/{id}/reschedule` (#472).
- Run the venue, organizer and coach conflict gates when `PATCH /v1/events/by_id/{id}` changes a camp's or one-off's organizer or coaches, and report every clash to the admins as `event.conflict_detected`, as creation does; the update is never refused for a clash (#473).
- Answer 404 `EVENT_NOT_FOUND` to `PUT` and `DELETE /v1/events/by_id/{id}/marketing` for a soft-deleted event; restore it first (#484).

### Bug fixes: enrollment rejoin and state

- Clear `withdrawnAtUtc` and `withdrawalReason` when a departed member rejoins by accepting an invitation or having a request approved, as assign already did; the old departure ended the new stint, so every session after it was refused as not enrolled (#465).
- Set `isTrial` from the path taken on every assign and rejoin: assign, accepting an invitation and approving a request make a paid enrollment, and a request, accept or assign is credit-checked against paid accounts. A former trial member was checked against their spent trial credit and refused with 422 `INSUFFICIENT_CREDIT`, or kept drawing trial credit instead of their package (#468).
- Refuse assign, assign-trial, accepting an invitation and approving a request with 409 `INVALID_STATE` while the member's previous departure has a deferred credit settlement pending; they can rejoin once the sweep has applied it (#469).
- `POST /v1/events/by_id/{event_id}/enrollments/approve` runs the member clash gate: approving a request that clashes with a programme the member is already enrolled in returns 409 `TIME_CONFLICT` with `conflicting_event_ids`, and the request stays `requested` (#466).
- `POST /v1/events/by_id/{event_id}/enrollments/remove` refuses a member who has already left (`withdrawn`, `removed`, `declined`, `rejected`) with 409 `INVALID_STATE` and leaves the row unchanged. Removing a member who had already left re-dated their `withdrawnAtUtc` and settled their credit a second time (#467).

### Bug fixes: auth and users

- Report a soft-deleted user's username as taken on `GET /v1/auth/username-available` (`available: false`); registering it was already refused with 409 (#505).
- Reject a `dateOfBirthUtc` that is not a UTC midnight on `PATCH /v1/users/by_id/{username}/reapply` with 422 `INVALID_DOB_NOT_UTC_MIDNIGHT`, as registration and profile edits do; nothing is changed (#506).
- Match the address on `POST /v1/auth/reset-password` without regard to case, as email uniqueness does; the new password is emailed to the address as stored (#508).
- Refuse `POST /v1/auth/login` for a user who has left with 401 `ACCOUNT_LEFT`, the code their tokens were already refused with; no tokens are issued and the last login is not recorded (#507).

- Answer `DELETE /v1/users/by_id/{username}` for a user who is already soft-deleted with 422 `ALREADY_DELETED` instead of 404; an unknown username still answers 404 (#523).
- Reject a `status` other than `active` on `POST /v1/users` with 422 and create no user: an admin creates active users only. An unknown value answered 500, and `registered`, `pending`, `blocked` or `left` created a user in that status (#522).
- Refuse `POST /v1/users/by_id/{username}/mark-left` for a `registered`, `pending` or `blocked` user with 422 `INVALID_STATE`; only an `active` user can be marked left, so reactivation can no longer make active a user who was never approved (#513).
- Remove `super_admin` from the `Role` enum: `POST /v1/users/by_id/{username}/roles` and `DELETE …/roles/{role}` reject it with 422 and leave the roles unchanged, and a data migration (`n4c5d6e7f8a9`) strips it from every stored roles list. It granted nothing; the super admin is `isSuperAdmin`, changed only by `transfer-superadmin` (#514).
- Refuse `POST /v1/credits/accounts` for the super admin with 422 `SUPER_ADMIN_CANNOT_HOLD_CREDIT`; no account is opened. The super admin is a housekeeping account and holds no credit (#519).
- Revoke the session on `POST /v1/auth/logout`: the access token presented, the refresh token issued with it and every pair `POST /v1/auth/refresh` issued from them answer 401 afterwards (`INVALID_TOKEN`, `INVALID_REFRESH_TOKEN`); the user's other sessions keep working. The request still takes no body. Tokens now carry a session id (`sid`) that refresh preserves; tokens issued before this release carry none and keep working until they expire. Adds `revoked_sessions` (migration `o5d6e7f8a9b0`) (#510).
- Accept `POST /v1/auth/logout` and `POST /v1/auth/change-password` from any logged-in user, `registered` and `pending` included; they answered 403 `ACCOUNT_NOT_ACTIVE` (#510).

### Media Descriptors

- Everywhere the public surface published a bare media uuid it now publishes a **media descriptor**: `{ uuid, mimeType, filename }`. `PublicEventResponse.coverMediaUuid` / `galleryMediaUuids` become `cover` / `gallery`, `PublicVenueResponse.imageMediaUuid` becomes `image`, `PublicProfileResponse.avatarMediaUuid` becomes `avatar` (so `EventResponse.coaches[]` and `GET /v1/public/staff` carry it too), and `GET /v1/public/club-info`'s `siteMedia` maps each purpose to a descriptor instead of a uuid — it is still *stored* as a uuid map and written that way, and a slot whose media has since been deleted or made private is dropped from the published map rather than handed out. A uuid alone was not enough to render with: the download URL carries no extension and every media *metadata* route requires a token, so an anonymous client had no way to tell a photo from a 44MB video and pointed an image widget at both. `mimeType` is the type of the stored file and picks the renderer on its own — every stored row is `image/*`, `video/*` or `application/pdf` — and `filename` is the name the download URL carries (#424, #426).
- Per-owner media link rows (`GET /v1/{users|events|groups|venues|evaluations}/by_id/{id}/media[/{tag}[/{mediaUuid}]]`, and the `POST`/`PATCH` that return a row) are reshaped: `{ tag, metadata, media, createdAtUtc, updatedAtUtc }`, where `media` is the same descriptor. The flattened `mediaUuid`, `mediaType`, `mimeType`, `filename` and `availableVariants` are gone — the uuid is `media.uuid`, as everywhere else. Request bodies are unchanged and still take `mediaUuid` (#424, #426).
- `GET /v1/media/by_id/{uuid}/download` accepts an optional trailing filename — `…/download/{filename}` — and answers `HEAD` as well as `GET` (it returned 405 `Allow: GET` before). The filename is ignored for the lookup; it exists so the URL ends in a real extension and a browser saves under a sensible name. `HEAD` is how a client asks what a **variant** is: it answers that variant's `Content-Type` and `Content-Length`, and 404s when the variant does not exist. Nothing per-variant is embedded in any projection (#424, #426).
- A media artifact that was never produced now answers 404 instead of a different file. A PDF uploaded with `preserveOriginal` gets no page render, and `?variant=poster` used to fall through to the PDF itself, answering a request for an image with a 4MB document and a 200 (#426).

### Media Types

- `media.mime_type` was named for the type of the stored file and held the type of the **upload**, which diverge whenever the file is converted — a PNG uploaded without `preserveOriginal` is stored and served as WebP while the column said `image/png`. #331 closed the route where a client *declared* a wrong type; the conversion route stayed open, because every one of its tests pinned `preserveOriginal: true`. The column is split in two, each named for what it holds: `mime_type` is the type of the stored file — what a download's `Content-Type` says — and `original_mime_type` is the uploaded type, beside `original_filename` and `original_extension`. `MediaResponse` gains `originalMimeType` and `filename`, loses the `ref` block #424 had nested in it (it duplicated `uuid` and `mimeType`, which the record already carries), and its `mimeType` changes meaning accordingly. Existing rows are migrated without touching the filesystem: the served extension follows from `media_type`, `preserve_original` and `original_extension` (#426).
- An upload whose type cannot be resolved from its bytes, its declared type or its extension no longer persists `application/octet-stream`. It falls back to the media type the server classified it as — `image/jpeg`, `video/mp4`, `application/pdf` — so every stored row's `mimeType` implies its `mediaType`, which is what lets the descriptor publish one field instead of two (#426).

### New Endpoints

- `POST /v1/events/by_id/{event_id}/terminate` `{reason, cutoffTimeUtc}` ends a programme at a cutoff and notifies members with `event.terminated` (payload `reason`, `cutoffTimeUtc`); `POST …/extend` `{cutoffTimeUtc, reason?}` moves it later or earlier (moving it earlier notifies members with `event.extended`); `POST …/extend-indefinitely` `{reason?}` removes it. All three act on the current schedule, require the cutoff to be an occurrence start at least 30 minutes ahead, and refuse once the cutoff has passed (422 `INVALID_STATE`). Audit actions `terminate_event` and `extend_event` record the cutoff before and after (#306, #374).
- `POST /v1/events/by_id/{event_id}/drop` `{reason}` calls off a one-off by cancelling its single occurrence (the reason appears as `cancelReason` on the occurrence in the occurrence listings); it returns 400 `CANCELLATION_LEAD_TIME_VIOLATED` inside the 30-minute lead time, 422 `PAST_OCCURRENCE` once the occurrence has started and 422 `CANCELLED_OCCURRENCE` when already dropped. `POST …/reinstate` restores it while it has not started (422 `INVALID_STATE` afterwards). Audit actions `drop_event` and `reinstate_event` (#306).
- `GET /v1/events/by_id/{event_id}/schedules` (admin/coach) and `GET /v1/myevents/by_id/{username}/{event_id}/schedules` list an event's schedules in timeline order: `{id, eventId, effectiveFromUtc, effectiveUntilUtc, startTimeUtc, endTimeUtc, rrule, venueId, organizerName, coachNames, sessions}` (#388).
- Terminating a programme releases every balance bound to it once the cutoff has passed: the hourly sweep moves each member's unspent credit to a general account keeping its validity window, with no penalty, notifies the member with `credit.released`, and records audit action `credit_released`. Terminate takes no `creditDisposition` (#374).
- `POST /v1/events/by_id/{event_id}/occurrences/{occurrence_time_utc}/attendance` now returns **200 with a body** instead of 204. The body is `{"marked": [{"membername", "status"}], "refused": [{"membername", "code", "message"}]}`. Members are settled independently: one member who cannot pay for the session is refused and reported while everyone else is still marked, where previously any failure aborted the whole batch. Deployments that do not run on credits receive the same shape with an always-empty `refused` list, so the response never varies with configuration (#294).
- `POST /v1/events/by_id/{event_id}/enrollments/remove` and `.../approve-withdraw` gain an optional `creditDisposition` object (`penalty`, `validFromUtc`, `validUntilUtc`, `reason`). On deployments running the credit system it is **required** when the member holds a balance bound to that programme: removing them without it returns 422 `CREDIT_DISPOSITION_REQUIRED` and the member stays enrolled, since nothing is converted automatically and the balance would otherwise be stranded. The remainder after a flat penalty moves into a new general account; a penalty that consumes the balance leaves nothing. The penalty is one figure for the departure, taken from multiple bound accounts oldest-first rather than charged per account. Sending the field to a deployment without the credit system, or for a non-programme event, returns 422 `CREDIT_DISPOSITION_NOT_APPLICABLE` rather than being silently ignored (#294).
- Enrollment transitions can now return 422 `INSUFFICIENT_CREDIT` on deployments running the credit system. `POST /v1/events/by_id/{event_id}/enrollments/assign`, `/assign-trial`, `/approve`, and the member's own `request` and `accept` each require the member to hold at least one usable credit for the programme at that moment. The check is against today's date, not the programme's start date, and nothing is deducted — credit is spent by attendance, not by joining. Programmes only: camps and one-off events never reach the credit subsystem (#294).
- Reject unknown fields on every request body with 422. `CamelCaseModel` now sets `extra="forbid"`, so a field the schema does not declare is refused instead of being silently discarded — previously such a request returned 200 with the operation not performed. This applies to every schema in the API, not just the handful that already opted in (`EventUpdate`). Clients sending misspelled or retired fields must remove them: known cases include `passwordHash` and `profileImageUrl` on user update, `overrideEditWindow` on bulk attendance marking, and `occurrenceTime` on assign-trial (#325).
- Require product identity to be supplied per deployment; there are no longer any club-specific defaults in code. The CORS allowlist (`CORS_ALLOWED_ORIGINS`), club naming (`CLUB_NAME`, `CLUB_SHORT_NAME`), public URLs (`LOGIN_URL`, and the new `SERVER_BASE_URL`), sender addresses (`EMAIL_FROM_TRANSACTIONAL`, `EMAIL_FROM_BROADCAST`) and email branding (`EMAIL_AFFILIATION`, `EMAIL_THEME_COLOR`) must now all be set in the environment; an instance that omits any of them fails at startup instead of silently inheriting another club's identity. The previous hardcoded production CORS fallback (one club's domain) is gone, so any deployment relying on it must now list its origins explicitly. `EMAIL_LOGO_URL` is replaced by `EMAIL_LOGO_PATH`, a path relative to the static mount that the server resolves against `SERVER_BASE_URL` — the logo is served from the API host, which differs from the member site `LOGIN_URL` names (#311, #361).

  only the attachments tagged for the member (a tag beginning `shared_`, and
  only once the evaluation is published), and the evaluation media links under

- Add `GET /v1/users/count` (admin or coach), reporting live user counts grouped by status: `{"byStatus": {"registered", "pending", "active", "blocked", "left"}, "total"}`. Every status is always present, zero included, and `total` is the sum of all of them. Soft-deleted users and super admins are counted nowhere, so the numbers stay consistent with `GET /v1/users`; note that `total` includes the `registered` bucket, which `GET /v1/users` omits unless asked for it, so it exceeds that endpoint's `total` by exactly the registered count (#308, #362).
- Add `GET /v1/capabilities` (any authenticated user, including one still awaiting approval), reporting what a deployment can do: `{"creditSystem": bool}`. Clients cannot learn this from `openapi.json`, because the credit endpoints are registered on every deployment so the published schema does not vary with configuration (#294); without this the only way to find out was to call a credit endpoint and interpret a 503, which needs a login and makes an error response part of the happy path. An object rather than a bare flag so later capabilities can join it without a new endpoint. Read-only — the credit system is deploy configuration and is not settable at runtime. Authenticated rather than public: every consumer of the answer is post-login, so deployment configuration is not published to anonymous callers (#339).
- Add the credit system, an optional per-deployment subsystem gated by `CREDIT_SYSTEM_ENABLED` (default **false**). Where it is disabled every credit endpoint still exists and answers 503 `CREDIT_SYSTEM_DISABLED`, so the API surface does not vary with configuration. Credit is held in named accounts with 8-character ids, each either bound to one programme or general, each with a validity window; balances derive from an append-only ledger and there is no PUT, PATCH or DELETE anywhere in the subsystem. Admin: `POST /v1/credits/accounts` (open; a bound account names the programme it is bound to), `GET /v1/credits/accounts/{accountId}` (look up by code alone), `POST /v1/credits/accounts/{accountId}/extend`, `.../reverse`, `.../transfer` (closes the account and creates the general account it moves into, after a flat penalty). ### New Features

- Restore evaluations as an optional module, off by default and enabled per deployment via `EVALUATIONS_ENABLED`, supplied through the deploy conf's `EXTRA_ENV` passthrough. ### Lifecycle Changes

- Extend the user lifecycle with a new `registered` status between sign-up and admin review. Previously the commit ran in dependency teardown after the response was sent, causing intermittent spurious 404s under read-your-write access patterns (#212).
- Camp conflict checks (`POST /v1/events/check-conflict`, `POST /v1/events/by_id/{event_id}/check-user-conflicts`, and the venue/organizer/coach checks) now respect cancellations and reschedules. A partially-cancelled camp keeps reporting conflicts on its surviving occurrences (it was previously dropped entirely), `until_time` is treated as exclusive to match occurrence listings, and per-occurrence overrides are honored: cancelled occurrences are excluded and rescheduled occurrences are checked at their new start/end instead of the original slot (#231).
- `POST /v1/events/by_id/{event_id}/reschedule` now re-validates the session timetable against the new window. A window change that leaves the existing `sessions` no longer summing to the occurrence duration is rejected with 422 `INVALID_SESSIONS_TOTAL` (matching create/update); previously the mismatch was stored silently (#240).
- Enforce email uniqueness at the database level for `POST /v1/users` and `POST /v1/auth/register`. A partial unique index over live (non-deleted) users now backs the `DUPLICATE_EMAIL` 409, closing a race where two concurrent requests could both create users with the same email. Uniqueness is now case-insensitive (`foo@x.com` collides with `Foo@x.com`), and a soft-deleted user's email is released for reuse (#204).
- Record the rejection `reason` in the `reconsider_user` audit-log entry's `details` for `POST /v1/users/by_id/{username}/reconsider`. The reason is now recoverable via `GET /v1/audit_log` (previously `details` was `null`) even after the user reapplies and the active review row is closed (#245).
- `POST /v1/auth/reset-password` (forgot-password) now actually resets the password: it generates a new password, emails it to the account holder, and only then persists the change (a delivery failure leaves the old password intact). Previously it minted a reset token that was discarded, so the flow was a no-op. The response is still a uniform 204 regardless of whether the email exists (#268).

### Validation & Authorization Changes

- `POST /v1/admin/reset-password/{username}` now requires the `admin` role instead of super-admin, so regular admins can reset user passwords (super-admins still pass; resetting a super-admin target is still rejected with 403 `CANNOT_RESET_SUPER_ADMIN`). The generated password is additionally emailed to the target user when they have an email on file; emailing is best-effort and never fails the request (#269).
- Reject manual-to-auto conversion when the group has members with 422 `MEMBERS_EXIST` (#11).
- Reject manual-to-semi_auto conversion when existing members fail the new criteria with 422 `MEMBERS_INELIGIBLE` (response includes the offending `membernames`) (#11).
- Direct add to a semi-auto group rejects ineligible non-staff users with 422 `NOT_ELIGIBLE`; coaches, admins, and super-admins are exempt (#11).
- Eligibility query and join-request creation against an `auto` group return 422 `AUTO_GROUP_NOT_JOINABLE` (#11).
- Direct member adds (single or bulk) auto-resolve a pending join request for the same user as `approved` (#11).
- Super-admins are invisible to group membership writes: `POST /v1/groups/by_id/{id}/members/byname/{name}` and `POST /v1/mygroups/by_id/{u}/join/{g}` return 404 `USER_NOT_FOUND` when the target is a super-admin; `POST /v1/groups/by_id/{id}/members/bulk` lists them in `notFound` (#11).
- `DELETE /v1/groups/by_id/{id}/hard` on a non-soft-deleted group now returns 422 `NOT_DELETED` instead of 500 (#11).
- Reject inverted DOB window on event create/update with 422 `INVALID_STATE` when `dobOnOrAfterUtc > dobOnOrBeforeUtc`. DOB bounds are floored to UTC midnight on write (#18).
- Enforce structured event eligibility on `POST /v1/events/by_id/{id}/enrollments/invite`, `assign`, `assign-trial`, and `approve`, plus on `POST /v1/myevents/by_id/{username}/{event_id}/enrollments/request`. Ineligible users are rejected with 422 `USER_NOT_ELIGIBLE_FOR_EVENT`; users with NULL `dateOfBirthUtc` or `gender` are ineligible for any event whose corresponding criterion is set. Existing enrollments are grandfathered: tightening event criteria does not auto-cancel them (#18).
- Restrict `POST /v1/events/by_id/{event_id}/enrollments/assign-trial` to events of type `programme`; reject one-off and camp events with 400 `INVALID_EVENT_TYPE` (#19).
- `GET /v1/myevents/by_id/{username}` filters out public events the user is ineligible for and has no enrollment on; events the user has enrolled in (active or terminal) remain visible regardless of current eligibility (#18).
- Reject `sessions` whose `periodMinutes` total does not equal the per-occurrence duration with 422 `INVALID_SESSIONS_TOTAL`; reject empty `sessions` arrays with 422 `INVALID_SESSIONS_EMPTY` (use `null` to clear). Updating an event's window such that the existing `sessions` no longer match, without supplying replacement sessions in the same call, also returns 422 (#18).
- Reject join-side enrollment mutations (invite, assign, assign-trial, approve, accept, request) on a cancelled event series with 422 `INVALID_STATE`; super-admin bypasses. Exit-side mutations remain allowed (#21).
- Camp events follow flag-don't-block conflict semantics: `POST /v1/events` and `PUT /v1/events/by_id/{event_id}` no longer raise 409 `EventConflictException` when the camp's venue or organizer overlaps another event, and join-side enrollment mutations (invite, assign, assign-trial, approve, accept, request) on a camp no longer raise 409 `TIME_CONFLICT` when the user has overlapping enrollments. Clients surface these overlaps via the dedicated check-conflict endpoints. Programmes and one-off events keep the existing blocking semantics (#16).
- Camp events require `rrule` to include `FREQ=DAILY` and a bound (`COUNT=N` or `UNTIL=...`); other shapes are rejected on create / update / update-for-future with 422 `INVALID_RRULE_FOR_CAMP`. `EXDATE` on a separate line is permitted (#16).
- Reject `POST /v1/events/by_id/{event_id}/occurrences/{occurrence_time_utc}/attendance` earlier than 30 minutes before the occurrence effective start with 422 `ATTENDANCE_NOT_YET_OPEN`; super-admins bypass (#22).
- Apply `ATTENDANCE_NOT_YET_OPEN` to super-admins as well: marking attendance before the open window is data invention, not audit correction. The 15-day edit-window and 2-hour leave-window bypasses are unchanged (#106).
- Compute the 15-day attendance edit window and the 2-hour leave-declaration window from the rescheduled effective start (`OccurrenceOverride.new_start_time`) instead of the original RRULE slot key (#22).
- Restrict `gender` and `dateOfBirthUtc` edits on `PATCH /v1/users/by_id/{username}` to super admins; self and regular-admin requests including either field are rejected with 403 `PROTECTED_FIELDS` (#86).
- Reject duplicate username or email on `POST /v1/users` with 409 `DUPLICATE_USERNAME` / `DUPLICATE_EMAIL` instead of returning 500 (#67).
- Reject non-UTC-midnight `dateOfBirthUtc` on user create / update / register and non-UTC-midnight `dobOnOrAfterUtc` / `dobOnOrBeforeUtc` on group and event create / update with 422 `INVALID_DOB_NOT_UTC_MIDNIGHT`. Group and event bounds are no longer silently floored on write; clients must send UTC-midnight ms values (`value % 86_400_000 == 0`). Backfill migration `m7n8o9p0q1r2` floors any legacy non-midnight rows (#100).
- `GET /v1/myevents/by_id/{username}/occurrences` now applies the same structured eligibility filter as `/myevents/by_id/{username}`: occurrences of public events whose `gender` / DOB bounds do not match the user are omitted unless the user has any enrollment (active or terminal) on that event (#117).
